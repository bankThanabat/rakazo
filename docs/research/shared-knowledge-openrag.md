# Shared staff and customer knowledge

Checked 2026-09-17 against official documentation and OpenRAG source at `5cf69da5`, the revision in `infra/compose/customer-sources.json`. These are design findings, not a live deployment test. See also [the existing runtime research](openrag-langflow-runtime.md).

## Verified capabilities and limits

- Docling represents sections, tables, reading order, provenance, and bounding boxes when the input supplies them. Its `HybridChunker` respects document structure and an embedding tokenizer's token budget. Page coordinates are conditional, so a citation contract must permit sources without them. [Document model](https://docling-project.github.io/docling/concepts/docling_document/), [chunking](https://docling-project.github.io/docling/concepts/chunking/)
- OpenRAG's documented default file ingestion uses Docling Serve, exports the result to Markdown, adds filename metadata, then applies Split Text. This does **not** establish that stock ingestion preserves Docling's structured provenance or uses its HybridChunker. URL ingestion uses a separate flow without Docling. [Ingestion flow](https://docs.openr.ag/ingestion/)
- OpenRAG exposes OCR and table parsing settings. Changing parser, chunking, or embedding settings does not reprocess existing documents. Reindexing therefore needs an explicit job and activation of the completed revision. [Ingestion configuration](https://docs.openr.ag/ingestion-configure/)
- The public API accepts multipart uploads at `POST /v1/documents/ingest`, returns an asynchronous task, and exposes task status. Duplicate replacement defaults to true. Deletion operates on filenames or filenames resolved from a filter. The upload router carries the supplied filename through its task mapping, and Langflow ingestion uses the original filename when present. `GET /v1/tasks/{task_id}` returns the task status and a `files` map whose entries carry `filename` and `status`; the `/enhanced` variant only adds failure metadata. [Task serialization](https://github.com/langflow-ai/openrag/blob/5cf69da5/src/services/task_service.py), [Document API](https://github.com/langflow-ai/openrag/blob/5cf69da5/src/api/v1/documents.py), [upload router](https://github.com/langflow-ai/openrag/blob/5cf69da5/src/api/router.py), [Langflow file service](https://github.com/langflow-ai/openrag/blob/5cf69da5/src/services/langflow_file_service.py)
- `POST /v1/search` returns `filename`, `text`, `score`, `page`, and `mimetype`. It does not return stable document, revision, or chunk identifiers, bounding boxes, or source URLs. It authenticates an API-key user and requires `search:use`. [Public search handler](https://github.com/langflow-ai/openrag/blob/5cf69da5/src/api/v1/search.py)
- Saved filter dimensions cover filenames, document types, owners, and connector types. Inline dimensions override saved dimensions; an empty inline object clears saved filters. A saved filter ID is consequently a mutable retrieval preference, not an immutable publication or authorization record. [Filter resolution](https://github.com/langflow-ai/openrag/blob/5cf69da5/src/api/v1/_filter_resolution.py)
- The pinned search service combines vector and keyword clauses through `bool.should` and obtains a user-scoped OpenSearch client. Its filename filter uses `term` or `terms`; missing dimensions impose no restriction. This is combined vector and keyword retrieval, but not OpenSearch's native `hybrid` query and normalization pipeline. [Search implementation](https://github.com/langflow-ai/openrag/blob/5cf69da5/src/services/search_service.py)
- OpenSearch supports a native hybrid query with a common filter applied to every subquery. Its document-level security restricts reads, not writes. ACL fields should use exact keyword values; text analyzers can alter identifiers. Filter and security behavior must be tested on the deployed OpenSearch version and identity configuration. [Hybrid query](https://docs.opensearch.org/latest/query-dsl/compound/hybrid/), [document-level security](https://docs.opensearch.org/latest/security/access-control/document-level-security/)
- OpenRAG combines Langflow, Docling, and OpenSearch in a self-hostable application. OpenRAG and OpenSearch use Apache-2.0 licenses; Docling uses MIT. Model weights and optional dependencies have their own terms. These project licenses do not establish permissions for every configured model. [OpenRAG repository](https://github.com/langflow-ai/openrag), [OpenRAG license](https://github.com/langflow-ai/openrag/blob/5cf69da5/LICENSE), [OpenSearch license](https://github.com/opensearch-project/OpenSearch/blob/main/LICENSE.txt), [Docling license](https://github.com/docling-project/docling/blob/main/LICENSE)

## Recommendations for Rakazo

These are proposed product rules, not capabilities supplied by OpenRAG.

1. Keep one space knowledge library. Rakazo owns source IDs, immutable revisions, ingestion status, access, and revocation. Both agent runtimes call one backend knowledge module. OpenRAG remains an ingestion and retrieval adapter.
2. The confirmed product rule is a per-source Internal toggle: on permits staff agents only; off permits both staff and customer agents, subject to existing space and agent permissions. There is no separate customer publication step. Defaulting new sources to internal is a recommendation, not a confirmed preference. Turning Internal on revokes customer retrieval immediately, including cached results and source downloads. Discard or restart pending customer replies that used newly restricted evidence; content already delivered cannot be recalled.
3. Activate a new source revision only after successful ingestion, retaining the old ready revision while processing. A mutable upstream filter ID is insufficient to identify that revision. For stock OpenRAG, investigate an opaque, globally unique filename per Rakazo revision, retaining the original display name in Rakazo. Send exact backend-derived filename lists. Never replace an active revision in place. Evaluate the current Internal toggle on every retrieval regardless of the revision used.
4. Treat filename mapping as an adapter compatibility contract. Source inspection supports the approach, but a real ingestion/search round trip must prove that two revisions coexist and remain independently selectable. Do not claim immutable upstream storage merely because a filename contains a revision ID.
5. Start with source-level citations mapped from the opaque filename, plus a page when the backend actually returns one. If exact passage IDs, table boundaries, or page highlights are required, extend the supported ingestion flow to retain structured Docling data and confirm how the search adapter exposes that metadata. Do not promise those features from the stock search response.
6. Keep search credentials and ingestion credentials on the backend. Use narrowly scoped service identities and OpenSearch access controls where supported. A shared administrator credential plus caller-provided filters is not tenant isolation. Prove isolation for the chosen deployment rather than assuming OpenRAG user ownership matches Rakazo spaces and audiences.

## Smallest compatibility experiment

Before implementation, create a rerunnable test against the pinned stack with fake documents. Ingest two revisions of one source and a second space's source. Verify exact revision selection, no cross-space result, Internal on denying customer access while allowing authorized staff, Internal off allowing both, immediate denial after revocation despite stale index data, failed ingestion remaining inactive, and citations identifying the retrieved revision. Include an attempted empty or wildcard filter override. This experiment decides whether the stock adapter is sufficient or a supported flow extension is necessary.
