# Shared document knowledge

Each space has one optional knowledge library. Staff agents and Langflow customer agents search the same active document revisions through Rakazo. Each source has an Internal switch: on permits staff only; off permits both audiences within the attached library. New documents are internal. Private agent memory remains separate.

The first person to configure the library owns its endpoint and encrypted credential. Space members can inspect documents and attach the library to their own agents; only the library owner can upload, replace, delete, change visibility, or rotate the credential. The endpoint follows the existing compatible-service network policy. Runtime secrets remain on the backend. No hosted provider is required.

Rakazo stores original files, source visibility, immutable revision keys and processing status. OpenRAG supplies Docling ingestion and OpenSearch retrieval. Its public API uses filenames, so each revision receives a unique opaque filename. A new revision becomes active only after its exact file succeeds; a failed or older replacement cannot overwrite the active revision. Search always sends an explicit allowed-key list. Empty scope returns no results without calling the provider. Results are checked against the latest source visibility and active revision after retrieval. Citations contain Rakazo source and revision IDs and optional page numbers; precise page highlighting is not promised by stock ingestion.

API and worker share one knowledge implementation and the existing job system. Queued and processing revisions are durable reconciliation input. A submitted upload whose task response was lost is marked failed instead of blindly resubmitted: OpenRAG provides no submission idempotency key. Replacing it uses a new key. A local read failure leaves the revision queued for the next pass. An upload the service refuses with a 4xx answer was never submitted, so it is marked failed without a cleanup tombstone. Operators may need to inspect failed or lost upstream tasks. Deletion removes access immediately and cleans up files and index entries asynchronously. The same cleanup removes any revision its source no longer points at: superseded, failed-then-replaced, or finished out of order. Deleting a space removes its library's files and index entries first, and is refused while an upload is still processing. An uncertain upload retains a cleanup tombstone and repeats removal, because upstream indexing could finish after the first deletion. Cleanup retries back off from 15 minutes to one day and stop after 12 attempts, preserving the row with a manual-cleanup error. Operators find paused cleanup with `SELECT id, "providerDocumentKey", "providerTaskId", error FROM knowledge_revisions WHERE "cleanupAttempts" >= 12`. They must inspect the upstream task before removing its exact document key and tombstone. Resetting `cleanupAttempts` to zero and `cleanupAfter` to null resumes retries. Access stays revoked throughout. The adapter accepts a deletion 404 only when its body identifies the requested filename and the stock missing-document response; unrelated route or proxy errors remain failures. [Upstream deletion contract](https://github.com/langflow-ai/openrag/blob/5cf69da5/src/api/documents.py).

Customer tools use the existing expiring execution capability. Knowledge reads rerun through current access checks rather than replaying stored text. Restricting, deleting, or activating a replacement for a shared source invalidates active customer conversations attached to that library and hands them to staff. Existing generation checks cover automatic delivery, direct connector replies, and workflow steps. A request already dispatched to an external provider can complete; previously delivered content cannot be recalled. The whole turn is not automatically replayed because earlier business actions may already have succeeded.

Existing customer filters keep working until the owner explicitly attaches the new library. Attachment clears that agent's legacy filter and connection and advances its behavior revision. While a library is attached, publishing a legacy filter is rejected so the two grants cannot coexist. Detaching does not restore the old grant. Existing OpenRAG documents are not automatically imported or made customer-visible; upload the intended documents and set their Internal switches before attaching. Changing a library's backend URL requires a separate migration, so this version supports credential rotation at the same endpoint.

Web and Electron expose Documents beside Memory and Skills in agent settings. Mobile exposes Documents within Advanced settings, using a native picker, switches, deletion alert, and share sheet. The first version accepts PDF, DOCX, text, Markdown and CSV up to 10 MiB. Source downloads are authenticated staff operations; sharing a source with customer agents does not publish its original file on the web.

## Verification

Run `scripts/verify-shared-knowledge.sh` for adapter, database and browser checks with fake documents and provider responses. One offline conformance suite runs against every knowledge provider, including the test fake. The database suites cover isolation, replacement races, unknown and refused submissions, cleanup of superseded revisions, space purge, fresh retrieval and customer dispatch after revocation. Browser tests capture desktop and phone-width document controls. Native mobile uses the same contracts but its native picker and share sheet need a device acceptance pass.

The opt-in `pnpm exec tsx scripts/check-knowledge-openrag.ts --live` uses `KNOWLEDGE_BASE_URL` and `KNOWLEDGE_API_KEY` supplied to the command and tests two fake revisions and a third document standing in for another space against an isolated real stack. It verifies filename preservation, exact retrieval and that the third document stays out of the other scope, and removes its completed fixtures. Empty and wildcard scopes never reach the service, so the offline adapter tests cover them. Offline tests do not establish real parser, embedding, or deployment compatibility.
